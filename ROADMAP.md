# Roadmap

Improvements considered for the relay and the prompts but not made yet, each with what would bring it
forward. The yardstick is the owner's: quality first (correctness, then maintainability, performance and
architecture), then autonomy (the owner involved only when necessary), through few high-leverage changes.
Items are ordered by expected value.

| Item | Why not yet | Bring it forward when |
|---|---|---|
| **The autonomy drain.** Owner questions with a safe default wait for a decision point instead of stopping the run (stage 2 of `.agents_work/owner-routing/proposal.md`: the council records a deferral to the owner with a `decidedBefore` slice, the relay asks him at that slice's start, and never reports completion with one open) | Stage 1 (November 2026) raised the relay's own limits that sent most questions (in one long project run: 8 of 14 after the routing changes) and now shows, per topic, how many decisions reached the owner, how many took the recommendation and how long the relay waited for him; stage 2 changes the relay's guarantees and needs those measurements first | Stage 1 has run on a topic and its owner questions still stop the run for hours, most of them with a safe default |
| **Project standards instead of cases** (for one project: filing a failing row under a shown cause, admitting references, constants inside a calculation, bookkeeping; `.agents_work/owner-routing/proposal.md` section 2) | On trial in a long project run since 2026-11-12 (the owner's decision in its handoff): the owner judged that, when such questions reach him, he is too far from their details to decide them better than the council, the checks and the review | The trial's council decisions look right to the owner after a few days: then the project's own rules make them the rule for later runs |
| **A relay-owned plan with declared checks.** (1) Plan changes become structured proposals in a decision or result (add, split or narrow a slice; change its acceptance) that the relay validates and writes into `plan.md`; workers stop editing it by hand. (2) A strict plan schema in Markdown: `## S<n><letter>: title`, then `Needs:`, `Acceptance:` (bullets), optional `Checks:` and `Notes:`, nothing else; anything else is rejected naming the line, and the relay writes the plan only in that form. (3) The project declares its checks once in `relay.json` (test suites, UI tests, linters, type checks, builds: command, optional parameters such as a path, timeout; passing means exit 0), and `Checks:` names them per slice (`unit path=test/cli.test.js`); the relay runs them after each implementation and repair (a red check goes back to the implementer without a review; green ones go to the reviewer as evidence), registers a slice's acceptance tests among them, and runs the check the project marks as its full verification at the final verification, on the exact files | Workers report results honestly so far and the relay stops on malformed plans; it is a large change to the plan protocol, the prompts and the final verification, and the acceptance pilot should show first what independent tests are worth. Also covers the earlier items "relay-run acceptance tests" (rerun before accepting; a changed expectation judged, not silently accepted) and "relay-run full verification from a project-declared command" | After the acceptance pilot and stage 2 of the autonomy drain; sooner if a misreported result is observed, or hand edits break a plan again (two stops in one run so far) |
| **Actions after validation: local and external steps.** Builds that produce deliverables, commits, tags, pushes, pull requests and deployments, declared in `relay.json` with a kind (local action, or external: a one-way door) and run by the relay from a slice's `Then:` field (after the reviewer accepts it) or after the final verification passed on the exact files. External steps run only with authority the owner recorded (the handoff's authority section, or his yes to the step), exactly once across crashes (recorded before and after; an interrupted one is never re-run blindly: the step's status command, or the owner, decides), with credentials from the environment, never the plan. Deployment itself stays in the project's CI: the relay triggers its workflow and treats the result as a check | It needs the declared checks first, and it changes what the relay may do (today it never pushes): the authority rules need the owner's approval | After "a relay-owned plan with declared checks" works on a project |
| **Mechanical detection of weakened tests:** deleted tests, new skips and suppressions, gate exclusions | Weakening a gate now needs authority in the implementer, final-step and reviewer instructions | Weakening recurs despite that (cases so far: two final verification steps) |
| **The reviewer derives one independent input per acceptance clause** on slices without an acceptance phase | It risks padding, and the pilot will show what independent tests are worth | After the acceptance pilot |
| **Reviewer model or thinking changes; a separate provider for acceptance tests** | No evidence yet that either helps | Pilot data or an evaluation set shows a difference |
| **Helper sessions requested by a worker:** the relay starts a separate fresh session (given model, prompt, allowed inputs and output places), links its record into the step, and resumes the worker | The planner and advisor now put evidence production and independent readings in their own slices; one project run (November 2026) needed two such sessions, started by hand | Owner-launched helper sessions recur despite the planning rule |
| **A separate compaction limit for reviewers** | A reviewer stop in a project run came from production work misplaced in a review step; a higher limit would only have cost more | A reviewer's ordinary review, not misplaced work, hits the limit |
| **Risk routing from the actual diff** (more evidence for persistence, concurrency, numerical or real-time changes) | The council's decision classes cover part of it | Data shows risky changes passing with the ordinary evidence |

Project-owned, not here: mutation testing (`cargo-mutants --in-diff`), property and differential tests, and
architecture or dependency rules belong in each project's own verification, which the relay's workers run.
